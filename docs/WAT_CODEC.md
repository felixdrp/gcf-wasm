# The hand-written WAT codec: comparison with the Zig build

October 2026. `dist/gcf.wasm` is a complete GCF codec written by hand in
WebAssembly text (`src/wat/*.wat`). It implements the full ABI of the Zig
build of [gcf-zig](https://codeberg.org/felixdrp/gcf-zig) (`dist/gcf_zig.wasm`,
built from the `reference/gcf-zig` submodule):

* decoding of both profiles, deltas, the columnar graph output and the lazy
  tape;
* every encoder, including sessions, deltas, diffs and grouping;
* pack roots with SHA-256 and atomic delta application.

It exists to answer one question: **what does a careful hand-written module
gain or lose against the code `zig build` produces?**

**File names.** These measurements were taken before gcf-zig and gcf-wasm
became separate repositories, when the files had other names. Below, the
Zig build is `gcf_zig.wasm` (then `gcf.wasm`), the WAT codec with debug
names is `gcf.debug.wasm` (then `gcf_wat.wasm`), and the shipped WAT codec
without them is `gcf.wasm` (then `gcf_wat.min.wasm`). The split did not
change the modules: they rebuild byte for byte. Sizes and timings are those
of the build measured when each section was written; later work (sections 8
and 9) added about 3 KB.

Times are WAT time divided by Zig time (lower is faster). **The
hand-written codec is faster in every operation's geometric mean**, under
both JavaScriptCore and V8, from a module a fifth the size. What it costs is
development and maintenance effort (section 6).

## 1. Design

The WAT codec is a port of gcf-zig's `src/gcf.zig` and `src/encoder.zig`, function for
function, so that both builds accept and reject the same inputs with the same
error categories and lines, and emit the same bytes. The *machinery*
underneath is chosen by hand:

| File | Contents |
|---|---|
| `01_core.wat` | memory, bump arena (O(1) reset, 16 readable bytes after every block), growable scratch stacks, error globals, basic ABI exports |
| `02_simd.wat` | 128-bit scanners: find byte / any of 2–3 / escape characters, count, compare |
| `03_utf8.wat` | UTF-8 validation with an ASCII fast path (one `i8x16.bitmask` per 16 bytes) |
| `04_numbers.wat` | exact int64; decimal → double (Clinger, Eisel-Lemire, exact big-integer fallback); double → shortest (Ryu plus a short-decimal fast path); 64×64→128 multiply |
| `05_text.wat` | quoted strings, scalars, keys, field declarations, Murmur3 hash set, identity keys |
| `06_generic.wat` | generic-profile decoder: document, headers, objects, arrays, tabular rows, flattening, attachments, keyed maps, grouping, `[?]` trailers |
| `07_json_out.wat` | JSON writer (raw write cursor) and the decoding exports |
| `08_json_in.wat` | strict JSON reader (zero-copy strings) |
| `09_encoder.wat` | canonical generic encoder and `gcf_encode` |
| `10_graph.wat` | graph profile, graph deltas and generic deltas (decoding); columnar graph output; string and integer maps |
| `11_roots.wat` | SHA-256, stable merge sort, gcf-pack-root-v1, delta verify / decode + apply / graph delta apply |
| `12_tape.wat` | binary tape for lazy decoding; structural scanner diagnostics |
| `13_graph_enc.wat` | graph encoders: buffered (from JSON or from host-written columns, `gcf_encode_graph_cols`), session, delta; radix sorts; exact half-even score rounding |
| `14_delta_enc.wat` | generic full / delta / diff encoders, value grouping |
| `_tables.gen.wat` | **data only**, generated by `scripts/gen-wat-tables.ts` and self-checked: Ryu and Eisel-Lemire power tables, SHA-256 constants, kind abbreviations, error names and messages, named strings |

The build (`scripts/build.ts`) concatenates the fragments into one module and
compiles it with wabt. It uses simd, bulk memory, multi-value, sign
extension and saturating conversions, which every current engine supports.

Conventions that matter for speed:

* **Values travel in registers.** A value node is the triple
  `(tag i32, a i32, b i64)`, returned through wasm multi-value. Parsing a
  scalar touches no memory until the node is stored in its container.
* **Errors are a global, not a return value.** `$fail` records the first
  error; callers test `(global.get $err)` after each fallible call, as Zig's
  `try` does, but without an error union.
* **One allocator, called directly.** Each container is collected on a
  scratch stack and copied once, at its exact size, into the bump arena.
  Small fixed-shape objects (graph symbols and edges) go straight into
  exact-size blocks.
* **A raw output cursor.** Writers check capacity once per value and then
  store bytes directly.
* **Sorting moves pointers.** The stable merge sort moves 4-byte pointers.
  Leading 64-bit keys are compared inline, and the records are gathered
  once at the end.

## 2. Verification

`bun run test` and `bun run test:oracle`, both part of CI:

1. **The main suites run unchanged against the WAT module** (the default
   of `bun run test`; `bun run test:oracle` runs them against the Zig build
   too, with `GCF_WASM=gcf_zig.wasm`):
   * `gcf_compliance`: all 323 official fixtures plus host API, robustness
     and SIMD cross-checks;
   * `gcf_encoder`: property tests, streaming, deltas;
   * `gcf_boundary`: bytes API and lazy decoding.

   358 / 358 pass.
2. **Every export compared byte for byte with `dist/gcf_zig.wasm`**
   (`test/gcf_wat.test.ts`). The test checks that the WAT exports exactly
   the Zig ABI plus one documented extension, `gcf_encode_graph_cols` (see
   section 8). For that extension the oracle is the Zig JSON path:
   `encodeGraph` through columns must give the same bytes on 2,000
   generated payloads full of odd values. Compared on each call: output bytes, `unsafe_ints` flag,
   error category, error line. Inputs:
   * every fixture wire, through `gcf_decode`, `gcf_decode_tape` and (graph)
     `gcf_decode_graph_columns`;
   * generated generic values: encoded with and without flattening,
     decoded, and decoded again after mutations;
   * 8,000 mutated graph and delta wires;
   * generated inputs for every encoder (graph, session, graph delta,
     generic full/delta/diff, grouping), clean and mutated;
   * pack-root and delta fixture inputs, plus 3,000 mutations.
3. **Independent references for the hand-written algorithms:**
   * number formatting against JS on 100k doubles;
   * number parsing on 90k strings plus the classic hard cases;
   * SHA-256 against `node:crypto` on every length from 0 to 300 and
     larger inputs.

During development the differential runs were larger: about 190k generic
decodes, 220k graph and delta decodes, 120k generic encodes, 100k
graph/delta/grouping encodes, 4k root/delta operations and 1.4k tapes. Every
run ended with 0 differences.

Three bugs found along the way are typical of hand-written wasm:

* **An unbalanced parenthesis.** The build failed while the previous
  binary stayed in `dist/`, and three benchmark rounds measured the stale
  module. The build now deletes the WAT module before compiling.
* **An eager `i32.or`/`i32.and` guard.** Both operands are always
  evaluated, so a guard like this let the merge sort dereference the
  element past an exhausted run. It is now control flow, and the allocator
  keeps 16 readable bytes after every block to make one-byte overreads of
  this kind harmless.
* **A record builder sharing the output cursor.** The builder was resumed
  in the wrong place by the encoders. It now publishes and restores the
  cursor.

## 4. Why the hand-written module is faster

The algorithms are the same: the same SIMD scanners, the same number
algorithms, the same tree shape (16-byte nodes, 24-byte members). The
difference is what the compiler adds around them. Counted on the
disassembled binaries with wabt:

| In the binary | `gcf_zig.wasm` (Zig, ReleaseFast) | `gcf.debug.wasm` |
|---|---|---|
| Instructions in total | 216,760 | **28,478** |
| `call_indirect` instructions | 1,617 | **0** |
| Functions that move the shadow-stack pointer | 401 | **0** |
| Multi-value function types | 0 | 37 |
| `memory.copy` instructions | 909 | 30 |
| 64-bit divisions and remainders | 63 | 4 |

1. **Allocator calls are indirect in Zig.** `std.mem.Allocator` is a vtable
   interface, so every arena allocation and every `ArrayList` or `HashMap`
   growth is a `call_indirect`. ReleaseFast inlines the call sites (1,617 of
   them) but cannot devirtualise them. The WAT arena is a direct call to a
   short bump allocator.
2. **Struct returns go through memory in Zig.**
   * LLVM's wasm32 C ABI does not use multi-value returns.
   * A `GcfError!Value` (a 16-byte union plus an error code) is therefore
     returned through a pointer into the shadow stack, which lives in
     linear memory.
   * 401 functions adjust `__stack_pointer` on entry and exit.

   The WAT returns `(tag, a, b)` on the operand stack, and engines keep it
   in registers.
3. **Error unions vs a global flag.** Every Zig `try` unpacks an error union
   from memory. The WAT tests one global.
4. **Hand-picked micro-optimisations**, each measured with a profile before
   and after:

   | Optimisation | Effect |
   |---|---|
   | Decimal digits divide by 100 as a multiply and shift (`(x · 0x51EB851F) >> 37`) | Removes the division per digit pair |
   | 16-byte vector moves for short copies | V8 lowers a variable-length `memory.copy` to an out-of-line call |
   | One capacity check per value at a raw write cursor | Replaces per-byte appends |
   | The encoder decides a row's `@N` prefix in a pre-pass | Rows go straight to the output, with no scratch buffer |
   | The merge sort moves pointers instead of records | Graph encoding: 12.3 → 8.9 ms |
   | Graph symbol and edge objects written into exact-size blocks; a one-byte test before the header checks | Graph decoding: 2.55 → 2.06 ms |

5. **Less code.** 28k instructions against 217k means less to compile and
   less instruction-cache pressure.

The comparison is not "Zig is slow". Zig ReleaseFast does exactly what it is
asked for on this target. Points 1–3 are consequences of a portable, C-ABI,
error-union style of code mapped onto wasm32, and a WAT author can simply
avoid them.

Notes:

* The WAT module includes a 16.9 KB `name` section: debug names for
  readable profiles and traps. Without it the module is 87.6 KB (50.3 KB
  gzip) and runs at the same speed, since engines ignore custom sections
  when executing; measured on tabular-large, 7.88 vs 7.95 ms in Node and
  8.35 vs 8.45 ms in Bun. What is lost: traps and profiles show
  `wasm-function[252]` instead of `sha_block`.
* Most of its data section is tables: Ryu 10.7 KB, Eisel-Lemire 11.1 KB,
  messages and names.
* Compile time is not compared, because V8 compiles wasm lazily and single
  measurements swing widely. In JSC the WAT module compiled in about
  0.8 ms against 2.7–3.5 ms for the Zig module.

## 6. What the hand-written module costs

* **Effort.**
  * 6,948 lines of WAT against about 4,440 lines of Zig.
  * The Zig version also leans on `std` for SHA-256, float parsing and
    formatting, and hash maps, all of which the WAT had to implement.
  * WAT lines are dense S-expressions: one Zig line is often 3–5 WAT lines.
* **No type system beyond the stack machine.**
  * Pointer and length mix-ups, wrong field offsets, eager boolean guards
    and unbalanced parentheses are all possible (section 2 lists the ones
    that happened).
  * The defence is the test suite, with the Zig build as an oracle.
    Without that oracle, writing this codec safely would have been much
    harder.
* **Simpler diagnostics.**
  * Error messages are static strings: one per category plus the specific
    ones that tests check.
  * Zig formats messages with the offending values (`row has 5 cells but
    the header declares 4`).
  * Categories and lines are identical.
* **Maintenance.** A spec change must be implemented twice and kept
  byte-identical. The differential tests make drift visible immediately,
  but they do not write the code.
* **Portability of the source.** The Zig engine is also a native library
  (`src/root.zig`); the WAT is wasm only.

## 7. Recommendation

**Keep the Zig source as the reference implementation and oracle.**

* It is the native Zig package ([gcf-zig](https://codeberg.org/felixdrp/gcf-zig)).
* It is far easier to change.
* It is what made the WAT codec safe to write.

**Ship the WAT codec as the WebAssembly module (done).**

* It has the same ABI and passes the same tests.
* It is 20–40% faster and 4.9× smaller, which matters most for browsers
  and edge workers.
* The npm package `@felixdrp/gcf-wasm` and the release ship it as
  `gcf.wasm` (`scripts/build-npm.ts`, `.github/workflows/release.yml`);
  the Zig module is not a release asset (the SIMD structural indexer is).

The maintenance rule follows from this: every spec change goes into gcf-zig
first, then WAT, with `bun run test:oracle` as the gate.

Both the npm package and the release ship it without the `name` section:
`dist/gcf.wasm`, 90,710 bytes. `dist/gcf.debug.wasm` keeps the names for
development and profiling. A test
checks that the two are byte-identical apart from that section, and the
main suites run against the shipped one.

Some of the WAT techniques could also be carried back to the Zig source:

* a non-vtable arena interface, called directly;
* value-returning hot paths that avoid error unions (an error flag, as
  here);
* vector short copies instead of `@memcpy` for short slices.

The WAT codec's explicit memory map also makes it the simplest base for the
constrained-memory build of [Option B](OPTION_B_PLAN.md).

## 8. Encoding graphs from JS values: columnar input

Encoding a graph from JS objects used to go through JSON: `JSON.stringify`
in JS, then the JSON reader in wasm. On graph-large (10,000 symbols, 15,000
edges) that path was slower than the TypeScript SDK (0.76–0.79×), because
the SDK works on the objects directly.

The time broke down as follows (Bun):

| Step | Time |
|---|---|
| `JSON.stringify` | 2.3 ms |
| Parsing that JSON in wasm | 2.3 ms |
| Encoding: sorting, resolving edges, writing | 6.2 ms |

Two changes:

1. **Columnar input** (`gcf_encode_graph_cols`, layout in
   [`WASM_ABI.md`](WASM_ABI.md)).
   * `host.ts` writes numbers straight into wasm memory through typed
     arrays.
   * It joins every string and encodes them with one `encodeInto` call. The
     offsets are UTF-16 lengths when the bytes written equal the code units
     (all ASCII), and exact UTF-8 lengths otherwise.
   * The JSON path converts its tree to the same columns, so one encoder
     serves both.
   * The fast path declines, and the JSON path runs, whenever
     `JSON.stringify` could read the payload differently: a non-plain
     object, `toJSON`, a bigint, an object in a recognised field, a string
     with a lone surrogate.
   * One difference is left by design: members the graph encoding never
     reads (extra fields) are not inspected. An ill-formed string there is
     rejected by the JSON path but ignored by the fast path.
2. **Radix sorts.**
   * Symbols get two stable LSD passes on 64-bit keys: score descending,
     then distance. Edges get one pass on the packed source:target key, with
     the rare equal-key runs ordered by type.
   * Passes whose digit is the same for every key are skipped.
   * Both orders are total, so the output equals the comparison sort's.

Speed-up over the TypeScript SDK when encoding from JS values:

| Payload | Before | Columnar path | JSON path (WAT) |
|---|---|---|---|
| graph-large, Bun | 0.79× | **2.41×** | 1.37× |
| graph-large, Node | 0.76× | **2.03×** | 1.09× |
| graph-small, Bun | ~0.7× | **1.45×** | 0.83× |
| graph-small, Node | ~0.7× | **1.08×** | 0.67× |

These figures come from a focused measurement: medians of 15 batches,
running the TS SDK, the columnar path and the JSON path back to back. In
the full benchmark (`bench/README.md`, 13 October), graph-large encoding
from JS values came out at 1.88× (Bun) and 2.16× (Node).

Comparing the fast path with the JSON path also exposed a bug in
`toJsonText`'s fallback serialiser, used when a payload holds a bigint or a
16+ digit integer. Unlike `JSON.stringify`, it wrote holes as `[,]`
(invalid JSON) and `undefined` members as `null`, and it ignored `toJSON`.
It is fixed and tested.

## 9. Encoding generic data from JS values

After the graph work, tabular data was the one shape where encoding from JS
values was still slower than the TypeScript SDK (0.85–0.93× on
tabular-large).

The time broke down as follows (Bun):

| Step | Time |
|---|---|
| `JSON.stringify` | 3.8 ms |
| A host-side regular expression over the JSON text | 2.9 ms |
| JSON parsing in wasm | 4.5 ms |
| Encoding | 7.6 ms |

The regular expression looked for 16+ digit integer tokens: an integral
double ≥ 2^53 that `JSON.stringify` writes as digits, which the engine
would read as an exact int64. Five changes, all keeping the output
identical:

1. **JS-host numbers flag** (`gcf_encode` flags bit 1, announced by
   `gcf_features()`). The JSON reader itself reads an integer token of
   magnitude ≥ 2^53 as a double, so `encode(value)` sends the
   `JSON.stringify` output straight in and the scan is gone.
2. **Shape cache in the JSON reader.**
   * Each nesting depth remembers the keys of its last object (up to 32,
     all distinct).
   * When the next object repeats them in order (every row of a table),
     no duplicate check is needed.
   * The key is matched in place: same bytes between quotes, with no
     scan for the closing quote.
   * The key takes the cached pointer, so later field lookups and key
     unions succeed on pointer equality.
3. **Key unions** take a pointer-equality shortcut when a row repeats the
   union's key order.
4. **Quoting check.** A string starting with a letter skips the
   number-grammar and leading-character tests.
5. **Constant columns are detected on values instead of renderings.**
   Strings by bytes, numbers by numeric value (5, 5.0 and 5e0 render
   alike; so do -0.0 and 0). Before, every value of every row was rendered
   once just to compare it.

Results on tabular-large:

| Measure | Before | After |
|---|---|---|
| Encoding phase | 7.6 ms | 4.0 ms |
| JSON parsing | 4.7 ms | 4.05 ms |
| Speed-up over the TS SDK, Bun | 0.85× | 1.38× |
| Speed-up over the TS SDK, Node | 0.93× | 1.68× |

## Running it

```sh
git submodule update --init   # reference/gcf-zig, the Zig oracle (needs zig)
bun run test:oracle      # differential tests, then the main suites against the Zig build
bun run bench:wat        # speed (Bun and Node) and sizes, including the equal-scope
                         # Zig builds; writes bench/results/wat-vs-zig-*.json
```

The codec loads through the normal JS API, since the ABI is the same:

```ts
import { readFileSync } from "node:fs";
import { GcfCodec } from "./src/host";
const gcf = await GcfCodec.instantiate(readFileSync("dist/gcf.wasm"));
gcf.decode("GCF profile=generic\nname=Ada\n"); // { name: "Ada" }
```
